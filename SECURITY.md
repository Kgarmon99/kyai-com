# Security Policy

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Report it through GitHub's private vulnerability reporting instead:

1. Go to the [Security tab](https://github.com/Kgarmon99/kyai-com/security/advisories).
2. Choose **Report a vulnerability**.
3. Describe the issue, the affected URL or file, and how to reproduce it.

That channel is private between you and the maintainers. If it is unavailable,
open a public issue that says only that you have a security report and asks for
a private contact — no details — and a maintainer will follow up.

Expect an acknowledgement within 7 days. We will tell you when the issue is
confirmed, when a fix ships, and we will credit you in the advisory unless you
ask us not to.

## What is in scope

KYAI is a static site plus serverless API routes, so the useful reports are:

- Exposure of personal data, especially subscriber emails or contributor
  contact details, in the repository, the git history, the built site, or an API
  response.
- Authentication problems in the review and ingest endpoints
  (`X-KYAI-API-Key`), including privilege escalation between the contributor,
  editor, and admin roles.
- Injection or data-integrity problems in the submission pipeline that would
  let unreviewed content reach the public site.
- Secrets committed to the repository or leaked through the build output.
- Cross-site scripting in rendered signal, region, profile, or toolkit content.

Out of scope: volumetric denial of service, findings that only affect a fork's
own configuration, and reports generated by a scanner with no demonstrated
impact.

## Handling personal data

KYAI publishes everything in `dist/client` to the public web, and the site is
built directly from this repository. Two rules follow from that:

- Never commit subscriber records, contact details, or any other personal data.
  `data/subscribers.json` is gitignored for this reason, and
  `scripts/smoke-test.mjs` fails the build if personal data reaches the
  published output.
- Never put real credentials in `.env.example`, issue templates, or test
  fixtures. Use `example.com` addresses and obvious placeholders.

If you believe personal data has already been published, report it through the
private channel above rather than in an issue, so it can be removed before
being drawn to wider attention.

## For contributors and forks

Set your own values for `KYAI_NEWSLETTER_NOTIFY_TO` and
`KYAI_NEWSLETTER_GITHUB_REPO`. These deliberately have no upstream defaults, so
a fork cannot accidentally deliver its subscribers to the KYAI maintainers.
